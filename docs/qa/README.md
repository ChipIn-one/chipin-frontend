# Памятка тестировщика: проверка релиза ChipIn

Короткая инструкция для того, кто проверяет новую версию сайта перед выкаткой. Знать код не нужно.

## 1. Когда начинается проверка

- Проверку запускает владелец (`syllik`) одной кнопкой на GitHub.
- Тебе приходит сообщение в Slack, в канал `#chipin-ci`, с упоминанием тебя. В нём:
  - ссылка на Preview (тестовая сборка сайта);
  - ссылка на задачу проверки на GitHub, она называется `Release QA <код версии>`;
  - ссылка на эту памятку.
- Сама задача проверки дальше называется **QA Issue**. Ты в ней назначен исполнителем.

## 2. Что внутри QA Issue

- **Immutable Preview URL** — адрес вида `https://chipin-frontend-….vercel.app`. Тестируй **только по этой ссылке**. Не `chipin.one` и не `dev.chipin.one`: там другая версия.
- **Included work** — список задач, которые вошли в релиз.
- **Checks** — чек-лист. Строки бывают трёх видов:
  1. **Шаг из задачи**: `#123: шаг => ожидание`. Сделай шаг и убедись, что видишь ожидаемое.
  2. **«check against the Acceptance of #N»**: у задачи нет готовых шагов. Открой задачу #N по ссылке в строке, найди раздел **Acceptance** и проверь те пункты, которые видно в интерфейсе. Пункты про код, тесты и настройки пропусти.
  3. **SMOKE-SHORT**: пять общих проверок. Они появляются, если релиз затронул вход, переходы между страницами, связь с сервером, офлайн-режим, тему или саму сборку сайта:
     - вход через Google на Preview — открывается Dashboard;
     - создать расход в группе, поделенный поровну — расход появился в списке, баланс изменился;
     - второй участник открывает Balances / Settle up — видит такой же баланс;
     - переключить язык и тему, обновить страницу — оба применяются без мигания и сохраняются после обновления;
     - выйти из аккаунта и обновить закрытую страницу в том же браузере — сайт снова просит войти.
- **Build-affecting changes** и **No QA needed** — справочные списки, проверять по ним отдельно ничего не нужно.

Галочки в чек-листе — только для тебя, чтобы не потеряться. Результатом они не считаются.

## 3. Как написать результат

Напиши **новый комментарий** в QA Issue. Первая строка — ровно одна из трёх, заметки — со второй строки.

**`QA PASS`** — всё из чек-листа работает как ожидается.

```
QA PASS
Android Chrome и ноутбук Chrome, все строки чек-листа пройдены.
```

**`QA FAIL`** — что-то из релиза работает неправильно. Сначала заведи баг (раздел 5), потом напиши:

```
QA FAIL
Расход не появляется в списке после сохранения: https://github.com/ChipIn-one/chipin-frontend/issues/600
```

**`QA BLOCKED`** — проверить не получается по причине, не связанной с релизом: Preview не открывается, вход не работает, сервер staging не отвечает, нет нужных данных. Причину — в следующей строке.

```
QA BLOCKED
Preview не открывается: страница пишет 404.
```

Когда блокер сняли, проверь и напиши **новый** комментарий в том же QA Issue (`QA PASS` или `QA FAIL`).

## 4. Частые ошибки

- **Правка старого комментария не засчитывается.** Если исправить или удалить комментарий с результатом, прежний результат отменяется, и владельцу придёт сообщение об этом. Нужен новый комментарий.
- **Только точная первая строка.** `QA PASSED`, `**QA PASS**`, `QA PASS.` не засчитываются. Регистр и пробелы по краям не важны: `qa pass` подойдёт.
- **Не начинай обычные заметки со слова «qa».** Комментарий, который начинается с «qa», но не является результатом, будет отмечен как ошибка. Пиши заметки с другого слова или под строкой результата.
- **Засчитывается только назначенный тестировщик.** Комментарии владельца, ботов и других людей результатом не считаются.
- **Только открытый QA Issue `Release QA …`.** Результат в другой задаче или в закрытом QA Issue не засчитывается. Сообщения в Slack тоже не считаются.

## 5. Как завести баг

1. Открой форму Bug: https://github.com/ChipIn-one/chipin-frontend/issues/new?template=bug.yml
2. Заполни поля:
   - **Problem** — шаги, которые ты делал; что увидел; устройство и браузер; ссылка на Preview.
   - **Outcome** — как должно быть.
   - **Acceptance** — строка для повторной проверки: `- [ ] QA: шаг => ожидание`.
   - **Dependencies** — можно оставить пустым.
   - **References** — ссылка на QA Issue.
3. Тип, приоритет и остальные поля проставят агент или владелец.
4. Вставь ссылку на баг в QA Issue и напиши комментарий `QA FAIL` (раздел 3).

## 6. Что происходит дальше

- **`QA PASS`** — владелец выкатывает эту версию на `chipin.one`.
- **`QA FAIL`** — баг исправляют, потом начинается новая проверка с новым QA Issue. В ней будет строка из Acceptance бага — это повторная проверка.
- **`QA BLOCKED`** — владелец снимает блокер, после этого ты пишешь новый результат в том же QA Issue.

## 7. Устройства и аккаунт

- Проверяй на Android и на ноутбуке. iPhone нет: iOS проверяет владелец, когда получается.
- Входи своим аккаунтом Google.
- Где нужны два человека (друзья, общий расход, Settle up), второй участник — владелец.
- Время на проверку не учитываем, торопиться не нужно.
