# Frontend e2e tests (Playwright)

The e2e suite checks the app in a real browser against the staging API (#663): the smoke below and the [money-critical flows](#money-critical-flows). Pull requests run it in desktop Chromium; every release candidate runs it on five browser profiles against its immutable Preview ([release browser matrix](#release-browser-matrix)). The smoke mirrors items b to e of `SMOKE-SHORT` ([`release-qa.md`](engineering/release-qa.md), `scripts/release-qa/impact-rules.mjs`, where they carry `automated: true`); item a, the Google sign-in, stays manual because Google OAuth cannot be automated, and so does the real-phone check.

| Test                                                            | SMOKE-SHORT |
| --------------------------------------------------------------- | ----------- |
| an equal-split group expense is listed and changes the balance  | b           |
| the other participant sees the matching balance in Balances     | c           |
| language and theme apply without a flash and survive a reload   | d           |
| after log out, reloading a protected page asks to sign in again | e           |

Code: `apps/app/playwright.config.ts`, `apps/app/e2e/specs/` (tests), `apps/app/e2e/support/` (target guard, provisioning, fixtures, global setup, UI helpers).

## Money-critical flows

`apps/app/e2e/specs/money/` covers the flows of #667, named by KB requirement IDs where one exists. Each test arranges its preconditions through the staging API, does the checked action in the UI and asserts the amounts as shown, for both participants where two are involved (each in its own signed-in context).

| Test                                                                                | Flow                       |
| ----------------------------------------------------------------------------------- | -------------------------- |
| EXP-011: an expense split by amounts gives each participant their own share         | unequal split              |
| SET-007: a partial payment leaves the remaining debt and appears in both activities | settle up, activity        |
| SET-007, BAL-003: paying the full debt settles both participants                    | settle up                  |
| EXP-044: editing the amount recalculates both balances                              | edit an expense            |
| BAL-004, EXP-050: deleting the expense settles both participants                    | delete an expense          |
| GRP-030: a second user joins through the invite link and both see each other        | join by invite link        |
| going offline shows the banner over the saved balance, and reconnecting hides it    | offline banner             |
| a balance with cents reads the same amount in English and in Russian                | money in both UI languages |

Not covered because the app does not have them with the production flags:

- **A note on a settle-up.** The API accepts an optional `note` (`CreateLedgerSettlementPayload` in the generated schema), but the settle-up form has only the amount (`components/modals/settle-up-modal`).
- **A change made offline that syncs after reconnect.** Offline expense writes are behind `VITE_FEATURE_OFFLINE_WRITES` (off), and every ledger, group and user write is refused while offline (`hooks/useLedgerMutations.ts`, `useGroupMutations.ts`, `useUserMutations.ts`), so nothing waits to be sent. The offline test checks the banner only.

The offline spec checks only data held in memory by the open page: no service worker registers on the dev server, so nothing is served from a worker cache.

The offline spec runs on every profile (`context.setOffline` sets `navigator.onLine` to false and cuts the page's requests in all three engines). It allows service workers only in Chromium (desktop and Pixel): Playwright controls the network of service workers (routing, network events) only in Chromium, so in Firefox and WebKit they stay blocked and the worker's offline cache is not covered there ([#735](https://github.com/ChipIn-one/chipin-frontend/issues/735)). The other specs keep service workers blocked and make no layout assumptions (a control that exists per layout is taken from the visible ones, and a control that is clicked must have exactly one visible match), so the release matrix runs them on every profile. On the Vite dev server no service worker registers (`devOptions.enabled: false` in `vite.config.ts`); on a Vercel Preview target the app's worker does.

The invite link is `<app origin>/group/join/<token>` (`buildGroupInviteLink`, `getChipInAppUrl` is `window.location.origin`). The app hands it out only through the native share sheet or the clipboard, which a test cannot read in every browser, so the invite test reads the token through the staging API and opens the link on the target. The token appears in the `goto` URL, traces and failure output; it is dead after the run's purge.

The split, edit/delete-expense and settle-up specs reload the writing user's page right after the write, without waiting for the persisted cache (written at most once per second), through `reloadAndReadGroup` (`e2e/support/ui.ts`): it awaits the group detail read (`GET /api/groups/{id}`) that follows the reload. A group restored from before the write may show first; it is replaced when that read lands, and the balance assertions then wait for the server's value (#724). The other participant opens a fresh context.

The invite test opens the invite link and clicks Join as soon as the confirmation shows: the Join button stays disabled (loading) until the session is restored (#730), and Playwright waits for it to be enabled. The test asserts that the join request succeeded.

All specs run on pull requests. Estimate: each money test takes about 8 to 20 s (two registrations, one or two contexts, two to four screens), so the eight add about 55 to 85 s with 2 workers, and the test step stays near 2 to 2.5 minutes, well inside its 10-minute timeout. If the measured job grows beyond that, tag the slowest tests `@release` and exclude them on pull requests with `--grep-invert @release`.

## Commands

Agents do not run e2e or builds locally; CI runs them (`.github/workflows/e2e-smoke.yml`, `e2e-sw.yml`). The commands below are for humans.

```bash
npx playwright install chromium   # once per Playwright version (firefox, webkit for those profiles)
CHIPIN_CONTRACT_SWAGGER_USER='<swagger-basic-user>' \
CHIPIN_CONTRACT_SWAGGER_PASSWORD='<swagger-basic-password>' \
npm run test:e2e -- --project=chromium
```

Without `--project` all five profiles run. `npm run test:e2e -- --list` (optionally with `--project=<name>`) lists the tests without credentials or network. `npm run test:full` and `npm run verify:full` never run the Playwright specs: Vitest excludes `e2e/**/*.spec.ts` and collects only the unit tests of the pure support modules (`e2e/support/*.test.ts`).

## Environment

- `CHIPIN_E2E_BASE_URL` (optional): the app origin. Unset, Playwright starts the Vite dev server on `http://localhost:5173` with the commit's code; it proxies `/api` to `https://api-dev.chipin.one` (`vite.config.ts`). Set, it must be a local `http://localhost:<port>` or `http://127.0.0.1:<port>` origin, or a Vercel Preview of this project, `https://chipin-frontend-<hash or git-branch>-sylliks-projects.vercel.app` (its `/api` rewrite also goes to the staging API). Other `*.vercel.app` hosts are rejected.
- `CHIPIN_CONTRACT_SWAGGER_USER`, `CHIPIN_CONTRACT_SWAGGER_PASSWORD` (required to run): the staging Basic credentials, the same ones as the [contract tests](contract-tests.md).
- `VERCEL_AUTOMATION_BYPASS_SECRET` (optional): Vercel's Protection Bypass for Automation secret, needed only if the Preview is behind Vercel deployment protection. It is used only with a Vercel Preview target and sent only to that exact origin (see [Safety guards](#safety-guards)).
- `CHIPIN_E2E_JSON_REPORT` (optional): adds Playwright's JSON reporter writing to that file; the release matrix reads its counts from it.

## Safety guards

- The target is checked while `playwright.config.ts` loads, before the web server, the global setup or any request: `chipin.one`, `www.chipin.one`, `app.chipin.one` and `api.chipin.one` fail with `Production e2e target is forbidden`; any other host, scheme, user info, query, fragment or path fails as not allowlisted.
- Provisioning always goes to `https://api-dev.chipin.one`; the production API is never a target.
- The Vercel bypass headers (`x-vercel-protection-bypass` with the secret and `x-vercel-set-bypass-cookie: true`) are added by a request route of each signed-in context only to document navigations whose origin equals the Preview origin exactly (scheme, host and port) and whose path is not `/api` or `/api/...` (`vercel.json` rewrites those to `api-dev.chipin.one`), never through `extraHTTPHeaders`. Vercel answers with its bypass cookie, which covers the page's other requests to the Preview. The secret itself therefore never goes to `/api`, the staging API, Google or any other host; the bypass cookie (a Vercel token, not the secret) is sent with the page's `/api` requests like every Preview cookie. A trace records the navigation headers: CI scans the artifacts for the secret and uploads nothing that contains it.
- Missing credentials fail the global setup with a message that names the variables, never their values. An unreachable staging API fails the global setup with a message that names it.
- The Basic credentials are used only by Node `fetch` in the support code, never by Playwright's `request` or a page, so they reach no trace or report; CI also scans the artifacts for them. Error messages name the method and path, never a body or header.
- Session material of the run's test users is not kept out of the artifacts: the browser carries each user's refresh cookie and receives access tokens from the app's own refresh calls, so a trace or the HTML report can contain them. These users are deleted by the run's purge, and CI uploads artifacts only after that purge is verified; an access token in an artifact may still be accepted until it expires if the backend does not reject tokens of deleted users. Only the Basic credentials are guaranteed absent.

## Provisioning and cleanup

1. The global setup uses the `runId` from `CHIPIN_E2E_RUN_ID` when it has the format `fe-e2e-<13-digit ms>-<12 hex>` (CI creates it this way), else creates a new one, and passes it to the workers.
2. Each test registers its own users with `POST /auth/test-register` under that `runId` (Basic auth). A refresh token rotates on first use, so users are not shared between tests.
3. Preconditions (friendship by invite link, a group with both users, for test c an expense) are arranged through the staging API with the users' Bearer tokens. The checked action goes through the UI.
4. Each user gets its own browser context with a working session and no sign-in UI: the `__Host-chipin_refresh` cookie from registration, host-only on the app origin (the app reaches the API through its own `/api` proxy), and the session hint `Chipin_authSessionHint=true` in localStorage. The app restores the session with a cookie refresh, as after a real sign-in.
5. After all tests, also after a failure, the global teardown calls `DELETE /auth/test-runs/{runId}` (retried once on failure), then purges again (also retried once) and fails if that second call still deletes users. Only then does it log the counts (`[e2e] purged run …: users=… groups=… expenses=… settlements=… activityEvents=…`) and write the marker `apps/app/test-results/.purge-verified` with the run id.

The run stays self-contained: no test user or its data is ever connected to an account outside the same `runId`.

## Browser settings

Five projects (`playwright.config.ts`): `chromium` (`Desktop Chrome`), `firefox` (`Desktop Firefox`), `webkit` (`Desktop Safari`), `pixel` (`Pixel 7`, Chromium) and `iphone` (`iPhone 15`, WebKit). The phone profiles have a phone viewport (412 and 393 px wide), touch, a coarse pointer without hover and a mobile user agent; the contexts made by the `signIn` fixture inherit them. The specs use `click()`, which works with touch emulation, and no hover-only interaction. All projects use `en-US` and a light color scheme at start. Service workers are blocked, except in the offline spec. Tests run fully parallel (each registers its own users), with 2 workers in CI. Trace, screenshot and video are kept only for failed tests, in `apps/app/test-results/`; the video is recorded by the `signIn` fixture for each user's context (Playwright's `use.video` does not cover contexts made with `browser.newContext()`) and deleted when the test passes; the HTML report goes to `apps/app/playwright-report/` and is never opened automatically. Both folders are git-ignored. Locators use role, label, placeholder and visible text; there are no fixed sleeps.

## CI

`.github/workflows/e2e-smoke.yml` (workflow `E2E`, job `e2e-smoke`) runs the whole suite, the smoke and the money flows, in the `chromium` project only (`--project=chromium`), on pull requests to `master` and on pushes to `master`, on the commit's code with the dev server and the staging API. Its steps live in the reusable workflow `.github/workflows/e2e-run.yml` (target `dev-server`), shared with the [release browser matrix](#release-browser-matrix), so GitHub shows the check as `e2e-smoke / run`. It is not a required check (the ruleset requires only `frontend-ci`).

- A `check` job reports whether the staging Basic secrets are available. Without them (forks, Dependabot) the `e2e-smoke` job is shown as skipped, with a notice saying why.
- `e2e-smoke` passes `e2e-run.yml` only the two Basic secrets, by name (no `secrets: inherit`, no Vercel bypass secret); there they reach only the steps that need them (the test run, the artifact scan and the final purge), never as an environment variable of `npm ci`.
- **Trust boundary:** code of a same-repository pull request runs in this job with the staging Basic secrets: its own `playwright.config.ts`, test and support code, and the install scripts of the packages in its lockfile. Anyone who can push a branch to this repository can therefore read these secrets. They grant only staging test provisioning (`/auth/test-register`, `/auth/test-runs/{runId}`), never production. The Playwright container is not a security boundary: it runs this test code with the test step's secrets and with the workspace and `RUNNER_TEMP` mounted read-write, and the lockfile's install scripts already ran on the runner (`npm ci`); the image only removes the apt and browser downloads.
- A pre-flight request fails the job with a message naming the staging API when it is down, before any test runs.
- A newer push to the same pull request cancels the older run; runs on `master` are never cancelled. npm is not cached, as in every workflow of this repository (`package-manager-cache: false`).
- **Playwright image:** the test step (the Vite dev server included) runs in the official image `mcr.microsoft.com/playwright:v<version>-noble`, pulled from Microsoft's registry (MCR), where `<version>` is the exact pinned `@playwright/test` version of `apps/app/package.json` (the job fails unless it is a strict `x.y.z`). The image carries the browsers and their system libraries, so no job runs `apt` or `playwright install` and nothing is cached; whatever Ubuntu mirror the runner gets no longer matters (#750). A separate step pulls the image with its own 5-minute limit, so a slow pull shows apart from the tests. Only that one `docker run` is in the image (not a job `container:`): every other step runs on the runner. It uses the `node_modules` of the runner's `npm ci` and the runner's Node 24 from `setup-node` (the `engines` version), mounted read-only at `/opt/host-node` and first on `PATH`, not the image's own Node; the container prints `node --version` first. It runs as the runner's user with `HOME=/tmp` (result files stay runner-owned; Firefox does not run as root), mounts the workspace and `RUNNER_TEMP` at their own paths, and receives only the variables of the test step, by name (`-e NAME`), plus `CI`. The container is named after the `runId`; an always-run step right after the test step removes it (`docker rm -f`), so a container left running by a cancel or timeout that killed the docker client cannot write results or register staging users after the artifact steps and the purge have started.
- The workflow creates the `runId` itself and passes it as `CHIPIN_E2E_RUN_ID`. A final step runs always, also after a cancel, a timeout or a crash of the test step, calls `DELETE /auth/test-runs/{runId}` with curl (the Basic credentials go through curl's stdin config, never its arguments or the log) and logs the counts; after the teardown's purge it deletes nothing.
- On failure, artifacts are considered only when the teardown's marker holds this run's id, i.e. after a verified purge. The report and test results are then scanned for the Basic password and Basic token, including zip files and the HTML report's embedded data, and uploaded with a retention of 3 days only when the scan is clean.

## Failures caused by staging

The suite runs against the shared staging API and deliberately has no retries, so a real flake stays visible. A staging outage therefore fails tests too. The `signIn` fixture records, in each user's context, every `5xx` answer to the app origin's `/api` and every `/api` request that got no answer (`e2e/support/serverErrors.ts`): method, path, status or error text, and time. The path has no query string, and every segment that is not a short lowercase word is replaced with `{id}` (a UUID) or `{token}`, so invite tokens and ids never reach the log. When such a test fails, it gets an `api-errors` annotation and an `api-errors.txt` attachment, and the log has a line `[e2e] API answered 5xx or failed during this test: …` naming the requests. A passing test reports nothing.

Read the statuses before rerunning:

- `502`, `503`, `504` or a request with no answer point to a staging outage window, not to the test's assertion. Seen on 2026-11-18 (runs 44336094806 and 44397956408, attempt 1): Cloudflare answered `502` to the cold-start `POST /api/auth/refresh` of a freshly opened context, in both workers at once; the app then showed the backend-down dialog ("ChipIn will be back shortly") or the signed-out landing, and the test timed out waiting for the group page (#778). Rerun the workflow.
- `net::ERR_INTERNET_DISCONNECTED` or `NS_ERROR_OFFLINE` after the offline spec's `context.setOffline` are caused by the test itself, not by a staging outage. A request the page cancelled itself (a navigation or reload) is not recorded, and an error text that is not a plain error code is shown as `other`.
- A `500` on the test's own write (an expense, a settlement, a join) is a bug to investigate, not one to rerun away.

The offline banner flake (#746) was a bug in the app, fixed by #749: a response to a request sent before going offline no longer marks the app online again.

## Service worker suite

`apps/app/e2e/sw.spec.ts` checks the app's service worker on one built app (spec 04 §2.11, criterion 5 scenario (a), and the parts of the 04-2d update policy that one deploy shows), in Chromium only (`apps/app/playwright.sw.config.ts`; Playwright sees and controls service worker traffic only in Chromium). It is a separate suite: its config allows service workers, has no global setup and needs no credential, because no user signs in. It never runs with `npm run test:e2e`, and Vitest excludes it like the other specs.

| Test              | Asserts                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| criterion 5 (a)   | after the first load of `/dashboard` the worker controls the page; `getRegistrations()` has exactly one registration, scope `<origin>/`, active script `<origin>/sw.js`, nothing waiting or installing; offline (`context.setOffline(true)`), a new navigation to `/dashboard` is answered by the worker (`fromServiceWorker()`, 200) with the bytes the host serves at `/app.html` (what the worker precached), no `/assets/` request fails, the app mounts and shows its signed-out dialog, and the registration is unchanged |
| no `workbox-*.js` | `inlineWorkboxRuntime`: `/sw.js` calls no `importScripts(`, and neither the page nor the worker's precache requests a `/workbox-*.js` next to the worker                                                                                                                                                                                                                                                                                                                                                                        |
| `visible` check   | a `visibilitychange` to `visible` makes the app call `registration.update()` (counted by a wrapper around it), the check settles with no new worker installing or waiting, the page was loaded once (taking control on first install reloads nothing: `registerType: 'prompt'`, `skipWaiting: false`), and the "New version available" toast is absent                                                                                                                                                                          |
| hourly check      | with Playwright's clock, while the page is online (`navigator.onLine`, no `offline` event yet), jumping one hour makes the app call `registration.update()` once more; after `context.setOffline(true)` and the app's `offline` event, the next hour starts no check                                                                                                                                                                                                                                                            |

The browser's own fetch of `/sw.js` during `registration.update()` reaches no Playwright event, so the `visible` and hourly checks count the app's `update()` calls instead. Each test starts in a fresh context, so the worker first precaches the whole build (about 125 files, fetched one after another): a few seconds in CI, up to a minute or two on a slow link; the test timeout is 4 minutes. There are no fixed sleeps: the tests wait on `navigator.serviceWorker.ready`, the controller and `expect.poll`.

Not covered yet: the prompt, "Later" and the forced update after 24 h need a second deploy with a newer worker. Scenarios (b) to (d) of criterion 5 covered the worker kill-switch, which 04-5a removed.

Agents do not run e2e or builds locally; CI runs them (`.github/workflows/e2e-smoke.yml`, `e2e-sw.yml`). The commands below are for humans.

Run locally against a Preview (any public `https://chipin-frontend-*-sylliks-projects.vercel.app` built from the code under test) or a local production build; the dev server registers no worker, so the config refuses to run without `CHIPIN_E2E_BASE_URL`:

```bash
npx playwright install chromium   # once per Playwright version
CHIPIN_E2E_BASE_URL='https://chipin-frontend-<id>-sylliks-projects.vercel.app' npm run test:e2e:sw
# or a local production build: npm run build && npm run preview, then
CHIPIN_E2E_BASE_URL='http://localhost:4173' npm run test:e2e:sw
```

`CHIPIN_E2E_BASE_URL` goes through the same allowlist as the main suite (production hosts are refused). `VERCEL_AUTOMATION_BYPASS_SECRET` is not used: this suite has no request routing, which would change how the worker answers, and Previews are public.

**CI.** `.github/workflows/e2e-sw.yml` (workflow `E2E service worker`, check `e2e-sw`, not a required check) runs on pull requests into `master` that change the worker or its build (`apps/app/src/app/pwa/**`, `apps/app/pwa.config.ts`, `apps/app/vite.config.ts`, the worker build scripts under `apps/app/scripts/`, `apps/app/src/helpers/appUpdate.ts`, `apps/app/src/shared/offline/network.ts`, `apps/app/vercel.json`, `apps/app/package.json`, `package-lock.json`) or the suite itself, and by hand (`workflow_dispatch`). It tests a commit against that commit's own Preview, with the tests of that commit. It has two jobs:

1. `resolve` runs only trusted code: `scripts/e2e-sw-resolve-preview.mjs` from the workflow's own ref (`github.sha`; on a pull request that is its merge commit; a sparse checkout with every branch's history), never from a dispatched commit, with no install. On a pull request the commit is its head, read from the event payload file (`GITHUB_EVENT_PATH`). On a manual run the input `target` is a pull request number, whose head must be in this repository (read with `pull-requests: read`; a fork's pull request is refused), or a full SHA, which must be reachable from a branch of this repository (a fork's commit is on none) and have a Preview (every pull request branch commit and every `master` commit is a Preview build, DEPLOYMENT.md). Reading the pull request is retried like the lookup below, for up to 2 minutes. It then waits (up to 15 minutes; a network error, a timeout, 429 or 5xx is retried at the next interval, any other GitHub error fails at once) for the GitHub Deployment of the commit in the app's Preview environment (`Preview` or `Preview – chipin-frontend`, [`scripts/deployment-environments.mjs`](../scripts/deployment-environments.mjs); never another Vercel project's), whose deployment and status are both posted by `vercel[bot]`, fails on a failed, errored or cancelled build, and validates the URL against the e2e allowlist. The optional input `preview_url` replaces the lookup; it must pass the same allowlist, but it is not checked against the commit, and the job says so in a warning. This job alone holds the token, with `contents: read`, `deployments: read` and `pull-requests: read`.
2. `e2e-sw` checks out the resolved commit, verifies that `HEAD` is exactly that SHA, and runs its `npm ci`, config and tests with `contents: read` only and no token after the checkout. The test step runs in the pinned Playwright image like [`e2e-smoke`](#ci) and checks the URL again; on failure the report and traces (no credentials in them) are uploaded for 3 days.

On a pull request the workflow file and the resolver come from the pull request's merge commit, as for any `pull_request` workflow, so they are exactly as trusted as the pull request itself; the split matters on a manual run, where the tested commit may be any branch's. No repository secret is used: Previews are public (`DEPLOYMENT.md`) and no user signs in. Inputs reach `run:` scripts only through `env` and are validated there. Fork pull requests are skipped (Vercel builds no Preview for them). Every step has a timeout and their sum fits in the job's. A newer push to the pull request cancels the older run.

## Release browser matrix

**Prepare frontend release QA** (`.github/workflows/prepare-release-qa.yml`, [`release-qa.md`](engineering/release-qa.md)) runs the whole suite against the immutable Preview URL of the release candidate on all five profiles before the QA Issue is created and the tester is pinged.

Jobs:

1. `resolve` (trusted master workflow code, no install, read-only `GITHUB_TOKEN`): picks the candidate as before (inputs or the zero-input walk), validates its `vercel[bot]` Preview (`chipin-frontend-<id>-sylliks-projects.vercel.app`, public), checks the SHA is inside current `master`, and outputs the SHA, deployment ID, Preview URL and fallback note.
2. `e2e <profile>`, one job per profile, `fail-fast: false`, shown as `e2e <profile> / run`: it calls the same `e2e-run.yml` as the PR smoke (target `preview`), taken from this trusted `master` SHA, and checks out the **candidate SHA**, so the tests are the code the Preview was built from (a test written for a newer screen never runs against an older build); the SHA is a `master` commit, which is at least as trusted as the pull request code the PR smoke runs. It first checks that the candidate's `playwright.config.ts` has every matrix project (one `playwright test --list` with `--project=` for each of the five). Playwright's "Project(s) … not found" with exactly `"chromium"` as the available projects means the candidate predates the matrix: every profile, `chromium` included, gets result `unsupported`, no image is pulled and no test runs, shown as "not in this candidate" and "The candidate predates the browser matrix"; any other error, another not-found (a renamed project) included, fails the job. It pulls the Playwright image of the candidate's pinned `@playwright/test` version (as in [CI](#ci); it holds every browser, so nothing is installed and no cache is restored or saved), creates its own `runId`, runs `npx playwright test --project=<profile>` in that image with `CHIPIN_E2E_BASE_URL` set to the resolved Preview (`playwright.config.ts` still rejects any target outside the allowlist, production included), and purges and handles artifacts exactly like `e2e-smoke`: final purge `if: always()`, report and traces uploaded only after a verified purge and a clean scan (Basic password, Basic token and the bypass secret). It also writes and uploads `e2e-result-<profile>`: `{version, profile, status: passed|failed|error|unsupported, passed, failed, flaky, skipped}`, counts from the JSON report, `error` when the suite produced none; the upload uses `overwrite: true`.
3. `prepare` (trusted master code, no install) runs after the matrix whatever its outcome (not after a cancel). It downloads the result files, reads one `result.json` per known profile at a fixed path (regular file, at most 4 KB, exact keys, integer counts, fixed status values; anything else is "no result") and the latest conclusion of each `e2e <profile> / run` job (the name GitHub gives the `run` job of `e2e-run.yml` called by `e2e <profile>`) from the GitHub API (`/actions/runs/{id}/jobs?filter=latest`, all pages). A profile passed only when its job succeeded and its file reports passed tests and no failure; a failure in either is "failed"; `unsupported` is "not in this candidate"; anything else is "no result". Then it creates the QA Issue and the handoff as before ([what the tester sees](engineering/release-qa.md#automation-and-the-human-tester)).

**Trust boundary.** The `e2e` job runs the candidate's `npm ci` install scripts, `playwright.config.ts` and test code with the staging Basic secrets and the optional `VERCEL_AUTOMATION_BYPASS_SECRET`, and `permissions: contents: read`. It never holds `CHIPIN_DEV_READ_TOKEN`, `CHIPIN_ISSUE_WRITE_TOKEN` or `SLACK_WEBHOOK_FE_RELEASES`; only `prepare` does, and it treats the result files as untrusted data (never as paths, Markdown or shell). Inside `prepare` the script only builds the Slack message; a separate step posts it through the shared `ChipIn-one/.github/automation/slack-notify-action` (v1.15.0) and is the only step that holds `SLACK_WEBHOOK_FE_RELEASES`, so the webhook never shares a step with the Issue tokens. A missing webhook no longer blocks creating the QA Issue; it is a warning. Workflow expressions never appear inside `run:` scripts; values reach them through `env`. The job reads and writes no cache. The browsers come from the official Playwright image, pulled from MCR by the exact version tag the candidate pins (not by digest); the test step gives the container only its own variables, by name, so the secrets keep the scope of that step, and the container runs as the runner's user with only the workspace and `RUNNER_TEMP` mounted. Production stays refused: `playwright.config.ts` still checks the target inside the image, and the test step fails before `docker run` when the Preview URL (`CHIPIN_E2E_BASE_URL`) is empty, so the matrix never falls back to the local dev server. The container is not a security boundary: it runs the candidate's test code with the test step's secrets and with the workspace and `RUNNER_TEMP` mounted read-write, and the candidate's `npm ci` install scripts already ran on the runner; the image only removes the apt and browser downloads.

**Runtime.** The profiles run in parallel, so the matrix adds the wall time of the slowest profile job: npm ci (about 1 minute), the pull of the Playwright image (about 1 minute; no apt and no browser download, whatever mirror the runner gets), and the 12 tests with 2 workers (about 2 to 3 minutes; WebKit is the slowest). Expected wall time: 5 to 7 minutes, within the 10-minute target of #666; the first rounds confirm it. The timeouts are hard caps, not that target: 7 minutes for the test step and 15 minutes for each profile job (set in `e2e-run.yml`), so a test step cut at its limit still leaves the purge room to run. A profile that hits a limit shows as "no result". The `prepare` job keeps its own 25 minutes.

**Re-runs.** "Re-run failed jobs" re-runs the failed `e2e` jobs and `prepare`. A re-run job replaces its profile's result file (`overwrite: true`), and `prepare` reads each job's latest conclusion, so the profiles that were not re-run keep their earlier results. `prepare` then finds the same-SHA QA Issue and comments the new result.

**Deployment protection.** The optional repository secret `VERCEL_AUTOMATION_BYPASS_SECRET` (Vercel: Project Settings, Deployment Protection, Protection Bypass for Automation) is needed only if Previews are behind Vercel deployment protection. With it, the public-Preview probe of `resolve` and `prepare` sends the `x-vercel-protection-bypass` header to the validated Preview URL only (the secret is in those steps' env and never logged), and the `e2e` jobs use it as described in [Safety guards](#safety-guards). Without it everything runs as before. A protected Preview also needs the tester to have Vercel access to open it.

**Verify after a change.** Run **Prepare frontend release QA** with no inputs: five `e2e` jobs, then `prepare`; the QA Issue starts with the matrix verdict and lists all five profiles before the handoff. For a deliberate break the candidate itself must fail, because the tests come from the candidate SHA and that SHA must be in `master`: merge a throwaway PR that makes one smoke assertion fail (for example an expected balance of `6` instead of `5`), run the workflow with that SHA as `candidate_sha`, check that the QA Issue starts with "The automated browser matrix did not pass" and that the Slack handoff has the "Автотесты в браузерах НЕ прошли" line, then revert the PR (the revert is a new candidate).
