# UI Rules

## Radix First

- Prefer Radix Themes primitives, component props, responsive props, and color props.
- Use `Flex`, `Grid`, `Box`, `Container`, `Card`, `Text`, and related primitives instead of rebuilding their basic layout in styled CSS.
- Use styled-components only when Radix props cannot express the requirement.
- Do not add another UI or styling library.

## Responsive Layout

Visual responsive behavior uses Radix responsive props first:

```tsx
<Grid columns={{ initial: '1', sm: '2' }} gap="3" />

<Flex
    direction={{ initial: 'column', md: 'row' }}
    align={{ initial: 'stretch', md: 'center' }}
/>
```

- Apply `{ initial, xs, sm, md, lg, xl }` values directly to Radix primitives when supported.
- Do not recreate a Radix-capable flex/grid layout with `display`, `grid-template-columns`, and media queries.
- JavaScript media-query hooks are reserved for behavior/lifecycle changes, never visual layout alone.
- A styled media query is allowed only when Radix cannot express the behavior.
- Do not hardcode breakpoints such as `767px`. An exceptional styled query uses a centralized project breakpoint helper aligned with Radix names; create it only when a real exception exists.

## Colors And Styled Components

- Radix components use Radix color/variant props.
- Styled-components use the typed project `themeColor()` helper.
- Do not add raw hex, RGB, HSL, or `var(--accent-*)`/`var(--gray-*)` values to ordinary styled-components.
- Raw colors are allowed only at technical boundaries such as PWA manifests, canvas, QR generation, or external formats that cannot consume theme tokens.
- Styled-only props use the transient `$prop` convention.

```ts
const StyledCard = styled(Card)`
    border-color: ${themeColor('gray6')};
`;
```

For conditional colors, compose styled blocks that still resolve every color through `themeColor()`; do not bypass the helper with raw theme keys or CSS variables.

## className And Inline Styling

- Do not introduce manual `className` styling for ordinary Radix or project components.
- The class generated internally by styled-components is allowed.
- Exceptions require an integration boundary: third-party widget, portal/root hook, centralized library override, or external API requiring a class.
- Avoid inline `style` in new and touched code; use Radix props or styled-components.

## Accessibility And Semantics

- Use native elements and Radix semantics before adding ARIA manually.
- Interactive behavior uses `button`, `a`, form controls, or the appropriate Radix primitive; do not make clickable `div`/`span` elements.
- Icon-only controls have translated accessible names.
- Inputs have associated labels and validation messages.
- Dialogs have a title and description; destructive confirmation uses `AlertDialog`.
- Preserve keyboard access, visible focus, and logical focus return.

## i18n And Money UI

- All user-facing strings, placeholders, ARIA labels, toasts, and validation messages use i18n keys.
- Add semantic keys to every supported locale and use interpolation/pluralization instead of string concatenation.
- Monetary output uses `basics/numbers/Amount` or a specialized basic that uses it internally. Feature/page code does not format amounts with `toFixed`, `Intl.NumberFormat`, or string templates.
- Monetary input uses the shared `AmountInput` when its contract fits.
- Split/payment controls keep stable dimensions across modes. Percent, exact amount, and share rows reserve
  the same control width; disabled or excluded participants show muted monetary output such as `0 USD`
  instead of changing row height.
- Per-participant split rows show the calculated monetary amount as muted secondary text below the
  participant name. Editable controls stay in a separate fixed-width column so long amounts and currency
  codes cannot move or resize the controls.
