# Frontend PR metadata

Contract (Task identity, routes, labels, owner and reviewer rules): [org `automation/pr-metadata.md`](https://github.com/ChipIn-one/.github/blob/master/automation/pr-metadata.md). This page lists only what is specific to the frontend.

- **Caller:** [`.github/workflows/pr-metadata.yml`](../../.github/workflows/pr-metadata.yml) calls the shared `pr-metadata-action`, pinned to an exact commit. It does not check out PR code.
- **Triggers:** `pull_request` to `master` from same-repo branches (opened, reopened, edited, synchronize; Dependabot PRs are filtered out), completed `Frontend CI` `workflow_run` for same-repo PRs (this also covers `ready_for_review`), and manual `workflow_dispatch` with the PR number and exact head SHA.
- **Credentials used by this workflow:** the job's scoped `GITHUB_TOKEN` for PR/Issue metadata and `CHIPIN_DEV_READ_TOKEN` for read-only canonical admission; no Project or Issue write credential. (The repository secret `CHIPIN_ISSUE_WRITE_TOKEN` is used only by `prepare-release-qa.yml`.)
- **PR bodies:** `npm run pr:create` ([`scripts/create-pr.mjs`](../../scripts/create-pr.mjs)) writes one `Task identity:` line and the `## Summary`, `## Tests`, `## Version impact`, `## Dependencies` and `## QA` headings; replace the prompts with verified evidence.
- **QA steps:** an implementation PR that changes UI-affecting paths (the list in [`scripts/release-qa/ui-paths.mjs`](../../scripts/release-qa/ui-paths.mjs), mirrored as `qaPolicy` in the org config) needs at least one QA step in its body: a `## QA` section with checklist steps (`npm run pr:create` adds it with a prompt; a label like `## QA (owner)` is allowed and does not pick the tester, `qa_login` of the release QA round does), or `- [ ] QA: <step> => <expected>` lines. Without one the run fails with a `QA:` blocker; `None`/`n/a` does not count. The release QA Issue lists these steps ([release QA](release-qa.md)); rule and parse: [org `automation/pr-metadata.md`](https://github.com/ChipIn-one/.github/blob/master/automation/pr-metadata.md#qa-steps-for-ui-affecting-prs--268). Change `ui-paths.mjs` and the org `qaPolicy` together.
- **Review and merge:** the reconciler never approves or merges; independent review and human-only merges remain required.

## CI event matrix

A task PR opens non-draft in one step with a complete body, so `ready_for_review` and body fixes are rare; when they happen they do not re-run the heavy gate (chipin-frontend#792).

| `pull_request` event                | `frontend-ci` ([`frontend-ci.yml`](../../.github/workflows/frontend-ci.yml))                                            | Cancels a running `frontend-ci` of the PR | `reconcile` ([`pr-metadata.yml`](../../.github/workflows/pr-metadata.yml)) |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- |
| `opened`, `reopened`, `synchronize` | Issue admission and the full gate for the mode (install, `verify:full`, build)                                          | Yes                                       | On the event and after `frontend-ci` completes                             |
| `edited` (body or title)            | Issue admission; the gate is reused when the newest earlier gate on the same head SHA passed, otherwise it runs in full | No: waits for it, then reuses its result  | On the event and after `frontend-ci` completes                             |
| `edited` with a base branch change  | Issue admission and the full gate                                                                                       | No                                        | On the event and after `frontend-ci` completes                             |
| `ready_for_review`                  | Same as `edited`                                                                                                        | No                                        | After `frontend-ci` completes                                              |
| `push` to `master`                  | Full gate for the diff from the previous push (release-QA evidence)                                                     | Never (own group per SHA)                 | Not run                                                                    |

- **Reuse rule:** [`scripts/ci-gate-reuse.mjs`](../../scripts/ci-gate-reuse.mjs) reads the `frontend-ci` jobs of earlier `pull_request` runs of this workflow on the head SHA, every attempt included, newest first. Runs where the gate never started (for example Issue admission rejected the body) are skipped. The newest gate decides: passed means reuse; failed, timed out, cancelled or still running means the full gate runs again. A lookup error also runs the full gate. A reused run still fails when Issue admission fails.
- **Required check:** every case reports the `frontend-ci` job on the head SHA, the only required check of the `master` ruleset, so a reused run satisfies it and a failed gate on that SHA stays failed until a gate on that SHA passes.
- **Newer `master`:** a reused run does not compare against a `master` that moved since the gate ran; `gh pr update-branch` (a new head SHA) runs the full gate.
